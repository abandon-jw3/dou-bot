# 2,000 群容量审查

2026-10-11，基于 main / 3907476 之后的未提交源码，保留 Slot.normalize、上下文中间件及上一轮框架审查改动。目标场景是 2,000 个群、每群每天约 50 次调用。源码契约修订为 1.14；npm 仍为 0.7.0。本轮只做离线验证，不连接 QQ、不修改业务示例或网站的 SDK 依赖，也不提交、推送或发布。

## 实现

- 去重与回复序号缓存分别维护按完成/释放顺序排列的到期索引。清理不再扫描全部活跃和保留记录；重新引用的回复记录移出到期索引，最后释放后重新计时。保持默认 TTL，未到期回复记录仍不可为了接纳新消息而淘汰。
- 去重缓存满时，从已经完成的记录中按最早完成顺序淘汰，不扫描活跃任务；这仍然是有容量上限的去重窗口。
- ApplicationSnapshot 新增 capacity、rejections 和 timing。计数不带事件内容或用户身份，快照修改不影响内部状态。排队与处理耗时区分 prompt 挂起和恢复。
- 新增显式 32 并发、2,000 队列、32 MiB 输入预算、50,000 去重记录、200,000 回复记录的验证配置；不改变 SDK 默认值。
- 新增当前 tarball 消费者和两种时钟模式的容量程序，CI 的四组 SDK 矩阵新增两小时虚拟时间回归与报告保存。使用方式及统计口径见 [容量指南](capacity.md)。

## 已完成的验证

Node 24.0.0 与 24.21.0 各通过 293 项 SDK 测试（本轮新增 6 项），148 个公开导出与 108 组双向类型检查通过。当前 tarball 的新监测消费者、历史 npm 0.6.0 和已发布 npm 0.7.0 消费者均通过。WS/Webhook 本地对照确认缓存与拒绝统计一致，处理计数一致。

覆盖率：行/语句 98.93%、函数 98.27%、分支 91.21%。业务示例的 36 项业务测试及 7 项开发进程测试通过；开发进程测试在沙箱内再次超时，在获准的沙箱外复核通过。文档站 18 项测试、39 页构建及 1,715 个本地链接通过。

两版 Node 分别完成两小时**虚拟时间**负载：各接纳 154,800 次调用，识别 6,192 次重复投递，覆盖 2,000 个群；容量拒绝为 0，155 次故意注入的发送失败全部被记录。每条调用的数据只加载一次。正常端到端延迟为模拟的 200ms，5% 慢请求为 2,150ms；这些数字来自可控时钟，不是公网延迟。

越过一小时窗口后，回复记录采样约 77,400 条，去重记录采样约 12,900 条，没有继续按累计调用量增长。关闭后队列、保留字节、两类缓存及到期索引、任务、信号、计时器、prompt、冷却记录均为 0。虚拟运行的实际耗时约 15 秒；它验证时间相关状态，不等于两小时真实持续运行。

## 缓存路径对照

使用相同 Node 24.21.0、同一主机和同一夹具，对照本轮改动前后编译产物。各保留 200,000 条去重和回复记录；诊断夹具将两类 TTL 都设为一小时，以便同时逐条到期，实际容量配置没有修改默认 TTL。

| 指标                              |     改动前 |     改动后 |
| --------------------------------- | ---------: | ---------: |
| 处理 1,000 次逐条到期             |  8,247.9ms |     46.0ms |
| 单次到期接纳的 expiresAt 字段读取 | 799,998 次 |       6 次 |
| 填充后、主动 GC 后的堆占用        |  92.48 MiB | 106.49 MiB |

新增索引用空间换取到期与淘汰效率，在这个合计 400,000 条记录的诊断中增加约 14 MiB 堆占用。这是一轮缓存路径对照，不是业务吞吐承诺。字段读取计数在计时完成后另行插桩，内存测量在插桩之前；RSS 与采样峰值不能视为 SDK 净占用。

## 真实计时负载

Node 24.21.0 的 65 分钟真实计时负载已通过，实际运行 3,901,160ms（含最后一批任务收尾）。使用相同 2,000 群配置，常态 20 次/秒，每十分钟前 30 秒为 50 次/秒，保持默认一小时回复缓存窗口。QQ HTTP 和数据加载仍为延迟夹具，未连接平台或数据库。

| 指标                                |                   实测 |
| ----------------------------------- | ---------------------: |
| 接纳并完成的调用                    |                 84,300 |
| 被识别的重复投递                    |                  3,372 |
| 容量拒绝                            |                      0 |
| 故意注入并正确记录的发送失败        |                     84 |
| 预期外错误                          |                      0 |
| 数据加载 / 处理器调用 / 发送尝试    |              各 84,300 |
| 95% 调用的端到端延迟桶上界          |                  250ms |
| 最大端到端延迟（含 5% 的 2 秒加载） |              2,177.0ms |
| 平均 / 最大排队等待                 |      0.078ms / 3.048ms |
| 负载产生器最大调度滞后              |                11.14ms |
| 堆 / RSS 采样最大值                 | 82.12 MiB / 232.58 MiB |

一小时后的回复记录采样维持在 77,406～77,407 条；接纳总数继续增长，记录没有随累计调用数无限增长。最终收尾快照为 77,381 条回复记录、12,881 条去重记录；随后关闭验证确认任务、信号、计时器、事件字节、缓存及到期索引等全部归零，进程正常退出。

内存数字包括 Node、合成 HTTP 响应、缓存与报告采样，并不等于 SDK 净占用或严格峰值。GC 后及 GC 前采样存在明显波动；本次 65 分钟结果不能证明多日业务运行无泄漏。上述延迟在给定的模拟加载及发送延迟下获得，不能替代实际 QQ、数据库或文件处理的验收。
