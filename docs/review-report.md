# dd-bot 开发草案严格审查记录

日期：2026-09-29 · 审查对象：设计草案 1.0 及公开 API 声明

这是设计阶段的历史审查，文中的“未实现”描述对应当时状态。当前 SDK 与实机结果见 [验证记录](./validation-report.md)，最新设计契约已更新至 1.2。

结论：发现 **9 组实质性问题，其中 6 组 P1、3 组 P2**。已将设计和类型层的修订同步写入 [开发方案 1.1](./development-plan.md) 与 [公开 API 声明](./public-api.d.ts)。这次审查验证了若干协议模型和依赖行为；项目还没有 SDK 实现，因此不能将这些结果表述为完整框架已通过运行时测试。

P1 表示按原草案直接实现可能造成鉴权绕过、丢消息、资源失控或关闭失败，必须在开发前修正；P2 表示会形成明显的契约歧义、类型漏洞或测试盲区。

## 审查发现与修订

### R1 · P1：无签名地址验证可成为事件签名预言机

**原位置：** 1.0 第 13 节。

地址验证签署 `event_ts + plain_token`，事件验签验证 `timestamp + rawBody`，两者使用同一个秘钥。如果允许任意 plain_token，签名接口可被用于生成指定 Dispatch 字节的有效签名。仅检查公开的 AppID 无法阻止此问题。

**证据：** 使用虚构测试秘钥在本地重现，两种拼接得到的签名确实互相验证通过。没有连接真实机器人或利用在线服务。

**修订：** 无签名挑战限制十进制时间戳、大小、字符与新鲜度，禁止 token 包含 JSON 对象/数组起始符和控制字符；Dispatch 必须是合法对象信封、验签并检查签名时间。新增原始字节、过期/未来请求、重复 header 与签名预言机反例测试要求。

**保留验收项：** 实际 QQ 挑战 token 的格式与重推请求时间戳行为需实机确认。兼容失败必须明确处理，不可自动撤销安全边界。

### R2 · P1：原生 WebSocket 无法兑现有期限的强制回收

**原位置：** 1.0 第 1、6、12 节。

原方案一方面限定原生 WebSocket，另一方面要求连接失效、重连及关闭总期限内回收资源。Node 24.21.0 原生客户端没有公开 terminate 方法；关闭握手被对端忽略时，无法依照原 API 强制结束连接。

**证据：** 本地模拟网关不响应关闭帧，原生 close 调用 10.5 秒后仍处于 CLOSING。随后验证 ws 的 terminate 能释放同类连接，maxPayload 能在应用收到消息前拒绝超大报文。

**修订：** 用户已确认将 ws 增加为生产依赖。禁用压缩和自动重定向，显式设置完整消息大小；关闭握手超时后强制 terminate，不累计旧连接。接口依据见 [ws 官方文档](https://github.com/websockets/ws/blob/master/doc/ws.md)。

### R3 · P1：启动/关闭并发及清理钩子可能突破关闭保证

**原位置：** 1.0 第 5、6、9 节。

原文只限制任务排空时间，没有给停止 listener、销毁钩子和启动中的异步结果定义同一个期限。close 与 start 并发时，迟到的 hook、token 或 socket 还可能重新启用运行时；一个永不返回的销毁钩子也可能让 close 永远挂起。

**修订：** 使用 generation 与启动取消信号；close 同步进入停止态，迟到结果不得复活实例。停止入口、排空、销毁共用绝对期限，超时强关自有连接并返回 SHUTDOWN_TIMEOUT；清理异常汇总为 CLEANUP_FAILED。生命周期钩子接收 signal，所有清理失败继续执行余下步骤。

**验证边界：** 本次进行了契约审查，没有实现生命周期管理器；并发时序和销毁超时必须在实现阶段用可控 Promise 验收。

### R4 · P1：消息序号及未等待的发送任务存在丢失/冲突风险

**原位置：** 1.0 第 8、14 节。

去重设计允许同一 msg_id 携带不同 msg_idx 成为多个事件，但回复计数器属于各自上下文，会从 1 重复分配，导致同一原消息出现相同 msg_id+msg_seq。此外，仅等待处理器返回，不足以证明其未 await 的框架发送已完成。

**证据：** 最小状态模型中两个上下文均分配序号 1；按原消息作用域共享后分配为 1、2。这是设计模型检查，不是已有 SDK 的回归测试。

**修订：** 应用级 ReplyCoordinator 按机器人、场景、目标、原消息共享序号及发送链；独立保留回复状态，不随去重 LRU 淘汰而重置。OperationLedger 跟踪上下文发送/确认，事件完成前排空；结束后拒绝晚到的上下文调用。超限在接纳或发送前明确拒绝。

### R5 · P1：带凭证的 URL 构造和重定向策略不完整

**原位置：** 1.0 第 10 节。

“路径以 / 开头”不足以确保同源，`//host/path` 和 URL 解析中的反斜杠变体可以切换域名。凭证获取请求还携带 Secret，默认跟随重定向会引入额外的凭证发送目标。

**证据：** 本地 WHATWG URL 解析验证了上述跨 origin 情形。

**修订：** 校验原始路径并二次核对解析后 origin；拒绝 URL 中的凭证、片段和控制字符。token/API fetch 使用 redirect=manual，WS 禁止自动重定向。读取响应时限制字节数，错误正文和 cause 在进入日志前脱敏。

### R6 · P1：数量上限与输入错误处理不足以保证接纳语义

**原位置：** 1.0 第 11–14 节。

单条约 1 MiB、等待队列 1,000 条时，仅看条数仍可能保留约 GiB 量级的编码数据。慢 HTTP 请求和 WS 完整报文也缺少相应约束。若归一化器的一切异常都被当成坏输入确认，内部 bug 会被永久 ACK；若 WS 过载后仍接纳更高序号，恢复将跳过未接纳事件。

**修订：** 增加事件字节预算、HTTP 读取期限及并发上限、REST 响应上限；多资源使用原子预留/回滚。明确区分输入无效与实现异常，后者不确认。过载同步封闭当前 WS generation，游标冻结，容量恢复后才尝试 RESUME；恢复失败报告连续性无法确认。

**限制：** 编码字节预算不是 JS 堆内存精确上限；先确认后执行的进程内队列仍可能在进程崩溃时丢失任务，RESUME 也不保证平台一定重放。

### R7 · P2：DI 绑定身份、循环检测和元数据测试存在空白

**原位置：** 1.0 第 4、5、19 节。

菱形导入可能重复转导出同一个 Provider，不能一律当成歧义。异步工厂若先缓存 Promise 再判断循环，可能互相等待。noEmit 类型检查也不能证明构造参数的运行时令牌被保留。

**证据：** 编译并执行装饰器样例：值导入保留真实类令牌，import type 生成 Function；隐式派生类没有自己的 design:paramtypes，但反射查询可取得继承值。直接只读 own metadata 会遗漏这种依赖。

**修订：** 先按最终绑定身份去重，再判断歧义；同模块重复令牌拒绝；实例化前静态检查完整依赖图。v1 明确要求需要父类注入的派生类重声明构造函数。新增实际 ESM/reflect-metadata 验证，避免将编译器检查等同于 DI 实现已正确。

### R8 · P2：公开声明允许 6 组互相矛盾的数据

**原位置：** 1.0 public-api.d.ts。

原声明在 strict 模式下接受以下全部情况：

1. ButtonContext 声明 private，但 target 是 group。
2. 单独提供 msg_seq，没有 msg_id。
3. 同时提供消息引用与 event_id。
4. callback 按钮顶层 ID 与 options.id 不同。
5. 上传文件引用缺少机器人和 API 环境范围。
6. 通过中间变量把 Webhook port 传入 WS 配置。

**修订：** 使用相关联的判别联合、互斥 never 字段和作用域字段；同时规定运行时校验，因为 JS 或强制类型断言仍可绕过静态检查。补充跨 bot/跨沙箱媒体复用与无效按钮注册测试。

**证据：** 同一组 6 个赋值在原声明下产生 0 个诊断，在修订声明下产生 6 个诊断；正向使用示例仍通过。

### R9 · P2：错误回调和 logger 可能反过来阻断框架

**原位置：** 1.0 第 16 节。

异步 onError 如果被协议路径等待，可能拖住 ACK、恢复或排空；若超时后不断启动新的不可取消回调，又会累积悬挂任务。用户 logger 同步抛错也不能直接扩散到协议处理。

**修订：** 自定义错误回调使用有界串行队列；超时后本实例禁用该回调并回到兜底日志，不不断派生悬挂 Promise。协议路径不等待它，logger 抛错单独捕获。错误信息经过脱敏，不把完整平台正文直接输出。

## 仍需实机验证的发布门槛

- 当前机器人实际支持的 WS 链路、心跳 s/d 字段及 RESUME 重放行为。
- QQ 的挑战 token、签名时间戳和重试方式能否通过新增边界检查。
- API/token 默认域名、群/私身份字段、图片上传响应在当前环境的实际表现。
- Markdown、模板、键盘、交互确认及主动发送的实际权限和错误返回。
- 无持久化队列、无跨进程共享去重与序号状态的既定限制，需在 README 保留。

修订后的草案可作为实现基线；以上协议门槛验证通过前，不应标记为已完成 QQ 兼容验收。
