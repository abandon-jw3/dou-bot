# 容量配置与运行监测

本指南面向需要服务较多群聊的应用。配置项沿用已有 SDK；`snapshot().capacity / rejections / timing` 是契约 **1.14 的尚未发布源码 API**，npm 0.7.0 暂不提供这三个字段。示例应用、网站和技能继续使用 npm 0.7.0。

已有读取旧快照字段的代码保持可用；自行构造 ApplicationSnapshot 的类型化测试夹具需要补齐新增字段。

## 从调用量估算

群数不是执行并发数。2,000 个群、每群每天 50 次调用，相当于每天 100,000 次；平均分布到 24 小时是 1.16 次/秒，集中到 8 小时则是 3.47 次/秒、12,500 次/小时。活动开始时的高峰需要单独估算。

这里的调用量是实际进入框架执行流程的事件数。成功命令、Guard 拒绝、参数错误、附件处理、按钮和 prompt 回答都会消耗对应资源。没有匹配处理器的事件通常不会进入执行队列；注册原始消息 On 观察器后，相应的普通消息也会进入执行流程，不能只按成功命令计数。

并发槽会被中间件、Guard、业务等待、回复发送和收尾占用。持续吞吐粗略受「并发数 ÷ 平均占用秒数」约束，还需预留余量；更多并发不会提高同步 CPU 工作的处理能力。正在等待用户回答的 prompt 释放执行槽，但仍保留会话、事件及缓存记录。

## 显式配置一个部署起点

下面是 2,000 群容量验证使用的配置，不是新的 SDK 默认值，也不是 QQ 的平台配额或吞吐保证：

```ts
const app = await BotFactory.create(AppModule, {
  appId,
  secret,
  transport: { type: 'ws' },
  execution: {
    concurrency: 32,
    queueCapacity: 2000,
    queueMaxBytes: 32 * 1024 * 1024,
    dedupMaxEntries: 50000,
    replyScopeMaxEntries: 200000,
  },
});
```

| 资源             | SDK 默认 | 上述配置 | 含义                                                                     |
| ---------------- | -------: | -------: | ------------------------------------------------------------------------ |
| 执行并发         |        8 |       32 | 同时占用执行槽的事件                                                     |
| 普通排队容量     |    1,000 |    2,000 | 与并发数共同限制普通事件接纳；prompt 回答和恢复有独立的会话调度          |
| 保留事件字节预算 |   16 MiB |   32 MiB | 限制已接纳事件的输入字节，不包含整个进程、缓存、业务数据或上传缓冲区     |
| 去重记录         |   10,000 |   50,000 | 活跃事件始终保留；完成后默认保留 10 分钟，满容量可提前淘汰最早完成的记录 |
| 回复序号记录     |   10,000 |  200,000 | 最后一个引用释放后默认保留 1 小时，未到期记录不为腾空间而淘汰            |

数量、字节和缓存限制同时生效。200,000 条回复记录按一小时保留估算，可以为持续 50 条/秒的新消息所需的约 180,000 条记录留出部分余量；这不意味着业务可以达到 50 次/秒。实际工作中还需考虑仍在执行的任务和 prompt。

这份配置没有提高其他交互限制：pending prompt 默认最多 1,000 个，冷却记录默认最多 10,000 条。大量群同时发起追问或使用较长的用户冷却时，需要按会话数量和保留时间另行估算。`ctx.state` 的 64 项与上下文操作预算 32 次分别约束一次处理器执行和一个事件，不是全应用的数据总量。

不要只提高并发。默认 10,000 条、一小时的回复记录，在 8 小时内处理上述日流量时可能成为先遇到的限制。也不要随意缩短 TTL 或删除有效回复记录，否则重复投递或同一消息的后续分段可能重新使用已经发送过的 msg_seq。去重记录的有限容量也不构成跨重启的恰好一次保证。

框架按完成/释放顺序维护到期索引；每类记录的 TTL 固定，使用单调时钟，清理只检查到期的记录及后面的首个记录。重复引用会先从到期索引移除，最后释放后再重新计时。接纳、容量等待和读取监测快照时按需清理，不为每条记录创建计时器。

队列用于吸收短时高峰。QQ 官方当前的群聊被动回复窗口为 5 分钟、单聊为 60 分钟；过长的排队可能让回复过期，应用仍需留出实际查询及发送时间。规则见 [消息收发概述](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)。

## 读取容量与延迟

```ts
const snapshot = app.snapshot();
const { capacity, rejections, timing } = snapshot;
console.log({
  active: snapshot.queue.active,
  queued: snapshot.queue.pending,
  replyRecords: capacity.replyScopes.size,
  replyRecordLimit: capacity.replyScopes.limit,
  queueFull: rejections.queueFull,
  replyScopesFull: rejections.replyScopesFull,
  meanQueueWaitMs:
    timing.queueWait.count === 0 ? 0 : timing.queueWait.totalMs / timing.queueWait.count,
});
```

`capacity` 返回并发、队列、事件字节的配置上限，以及去重和回复记录的当前数量及上限。读取时会清理已经到期的缓存记录。快照是独立副本，修改它不会调整应用配置或内部计数。

`rejections` 是本实例创建以来的累计计数。每个被拒绝事件只计入第一个适用原因，顺序如下；所有项之和等于 `events.rejected`：

| 字段                | 原因                                         |
| ------------------- | -------------------------------------------- |
| invalidEvent        | 非法事件、非法输入字节数或超过单事件大小限制 |
| queueFull           | 普通事件的执行及排队名额已满                 |
| bytesFull           | 保留事件的总字节预算不足                     |
| acknowledgmentsFull | 自动按钮确认的控制通道已满                   |
| replyScopesFull     | 新消息需要的回复序号记录没有空位             |
| dedupFull           | 去重记录全部被活跃事件占用，无法安全淘汰     |

未匹配、重复投递和正在关闭不是以上拒绝项。这里统计执行器收到的事件；在 HTTP/WebSocket 层已经拒绝的原始请求不包含在内。已接纳事件中的 Guard 拒绝、参数错误、冷却拒绝、业务失败也不算接纳容量拒绝，应结合业务及错误监测判断。

`timing.queueWait` 与 `timing.processing` 各有 `count`、`totalMs`、`maxMs`，单位为毫秒：

- queueWait 每次初始调度或 prompt 恢复调度记录一次，因此 count 不一定等于事件数。
- processing 对开始执行且已经结束的事件记录一次，累计其占用执行槽的时长；包含 I/O 等待、回复和收尾，排除排队及 prompt 挂起。被 prompt 接收但没有独立执行的回答不单独记录一次 processing。
- 超时关闭会记录取消收尾前实际占用的时长。尚未结束的事件不进入 processing 聚合。
- 计数和最大值属于整个实例生命周期，关闭后仍可读取；缓存当前数量在关闭后归零。计算最近一分钟平均值应取两次 count/totalMs 的差，累计最大值不能当作该分钟最大值。
- 不保存用户 ID、消息内容或逐条历史，也不提供虚构的 P95/P99。百分位需要在专用负载程序或宿主监测中采样。

出现 queueFull 时检查处理时长和下游等待，出现 replyScopesFull 时检查消息率与保留窗口，出现 bytesFull 时检查事件大小。WS 通过断开后等待容量再恢复接入施加背压；Webhook 对接纳过载返回 503。它们不保证平台无限期保留或重投事件。

## 验证自己的负载

在源码仓库执行：

```sh
# 保留默认 TTL，用可控时钟验证两小时的到期和重复投递；不是两小时真实运行。
npm run benchmark:capacity -- virtual 7200000 virtual

# 真实计时 65 分钟，越过默认一小时回复缓存窗口。
npm run benchmark:capacity -- realtime 3900000 realtime
```

报告写入 `work/capacity-review/<label>.json`。程序使用 2,000 个群 ID，常态 20 次/秒，每十分钟的前 30 秒为 50 次/秒；20% 的请求集中到一个热点群，5% 的模拟数据加载耗时 2 秒，其余为 50ms，发送延迟 150ms。重复投递必须被识别，定期注入的发送失败必须与错误计数一致，每条有效调用只执行一次数据加载。

请求按预定时间到达，不等待上一条结束才发送。报告包含调度滞后、端到端延迟直方图、缓存数量、内存采样、运行时长和关闭资源计数。SDK 的运行依赖不增加；本工具使用内存传输与合成 HTTP 响应，不连接 QQ、不访问数据库或本地凭证。

离线结果验证框架的容量控制与受控负载行为，不能替代实际服务器、数据库、QQ 配额与公网故障条件下的验收。当前状态在单实例内，横向扩容需要另行解决路由、去重和 prompt 会话归属，不能简单启动多个相同接入进程来获得倍数容量。
