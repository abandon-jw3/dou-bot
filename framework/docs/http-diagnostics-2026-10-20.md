# 指标索引与出站对照（2026-10-20）

**保留指标索引优化；HTTP 试验代码恢复原实现。** 本轮 500/s 的指标样本中，SDK 平均 CPU 约下降 2%，延迟大致相近。没有证明吞吐上限提高；750/s 的出站 32、64 两档均未通过。

## 修改与范围

- 指标按阶段、账号、处理器、组件序号和操作类型分层查找，减少每次记录时的 JSON 字符串分配。只有接纳新指标系列后才创建分支，数量仍受 maxSeries 限制；快照顺序、标签、取消和采样规则不变。
- 新增标签维度、上下文修改、长名称、容量拒绝与编码边界回归。最初的最近标签缓存会拖慢标签频繁变化的场景，已放弃。
- HTTP 的解码器复用和单分块直接解码在微基准略有收益，但协议对照没有稳定的整体收益，因此没有保留；超时、取消、字节上限和原 HTTP 路径保持原样。
- 服务器 SDK、模拟 API 与监督器共用 1.5 核 / 1 GiB；WS 网关在本机，经反向 SSH 转发。使用内存持久化，不连接真实 QQ、SQL 或渲染服务；框架默认并发与生产依赖未改。

## 成本证据

- CPU profile 单列，不计容量。500/s 下各采样 20 秒，均位于测量段；开启指标时 start 自身约占主线程采样墙钟的 3.4%，位置样本集中在键序列化与查找。GC、原生 fetch、错误对象及日志处理也有成本。
- 上述是主线程墙钟采样，包含 idle；不是全进程 CPU 分配。嵌套调用不可相加，V8 后台线程也不能全部归为 GC。夹具使用自定义静默 logger，仍执行脱敏，不能把其日志成本当作默认不输出 debug 的开销。
- 独立进程三轮微基准中，50 万次指标记录的 CPU 中位值：重复标签约 170.7 → 107.1 ms，频繁变化标签约 177.9 → 117.4 ms。它们验证查找成本，不能外推为整框架同幅度提速。
