# 真实 SQL 接入 WS / Webhook 容量验收（2026-10-21）

**本轮最高复验通过档位：WS 总计 450/s，Webhook 总计 350/s，各通过两轮五分钟测试。500/s 未通过。** 这些是指定资源和合成负载下的已测档位，不代表精确上限或长期生产承诺。

## 基线与配置

- dd9ec6d 已提交、推送，[CI](https://github.com/abandon-jw3/dou-bot/actions/runs/39465520824) 全部 10 个任务成功后才启动验证。
- SDK 指纹保持 `efbd2880a235c874e078728023b9b3bb7f0286d94af2c49811e1c0e7fb0c10e7`；本轮只扩展压测工具和回归，没有修改 SDK 运行时、默认并发、版本或依赖。
- 正式工具指纹为 `aca29a4132aa2fa67367a3b8f9bdbea458947446faa915ebb49eaeee29bfa21f`。两端按同一源码编译，测量期间不编译或修改源码。
- 双账号约各承担 50% 流量，使用独立群 OpenID；负载覆盖 2,000 个合成群位置。速率指两个账号合计的首次事件，另外包含重复、prompt 续答及 503 重试。
- 执行并发 128、出站并发 32、SQL 池 25，阶段指标开启。SDK、HTTP 夹具和监督器共用 1.5 核 / 1 GiB；独立 PostgreSQL 17.6 使用 0.5 核 / 256 MiB，测试进程组不使用 swap。
- PostgreSQL 使用目标磁盘上的新目录，每轮新建并删除独立 schema。资料预载后按 `(app_id, user_id)` 读取含 256 字符字段的 JSON；每次上下文加载执行一次 SQL，再请求原有慢 HTTP 夹具。
- 发压端和 WS 网关在本机，经 SSH 接入服务器上的真实 SDK 传输链路。QQ API 为本机夹具，未连接真实 QQ、Nginx/TLS 或图片渲染服务。

## 五分钟复验

每轮另有 10 秒预热和 15 秒恢复。以下测量段全部接纳并完成，末段队列中位数为 0，无非预期终态；预设的权限拒绝、输入错误和业务异常单独计数。

| 协议    | 总速率 | 两轮计划 / 完成        | 成功业务 P95 | SDK 平均 CPU       |
| ------- | -----: | ---------------------- | ------------ | ------------------ |
| WS      |  450/s | 每轮 135,000 / 135,000 | 641 / 640 ms | 0.9623 / 0.9778 核 |
| Webhook |  350/s | 每轮 105,000 / 105,000 | 823 / 664 ms | 0.9968 / 0.9856 核 |

- P95 是发压端观察的端到端时间，包含 SSH、预设慢接口及 prompt 等待，不是框架自身的纯处理耗时。
- 四轮 SQL 读取均全部完成：WS 每轮 138,802 次，Webhook 每轮 107,966 次。客户端 SQL 调用 P95 分别为 43 / 44、39 / 37 ms，包含池等待、传输和调用方调度，不能当作数据库执行耗时。
- SQL 池存在短时等待，采样等待峰值为 WS 26 / 46、Webhook 8 / 7；没有 SQL 失败。PostgreSQL 平均 CPU 约 0.095～0.115 核，低于其 0.5 核配额；仅凭平均 CPU 或客户端延迟不能确定最终热点。
- 本轮关闭后任务、会话、SQL 池及等待项归零，全部测试 schema 删除。更长时间的缓存、内存与真实业务行为仍需另验。

| Webhook / PostgreSQL | 400/s | 48,000 / 48,000 |  1,945 ms |             62 | 未通过：仍有积压   |
| Webhook / PostgreSQL | 500/s | 45,680 / 60,000 | 13,837 ms |          1,983 | 未通过；发压不完整 |
| WS / 内存            | 500/s | 60,000 / 60,000 |    610 ms |              0 | 通过               |

| Webhook / 内存       | 500/s | 50,763 / 60,000 | 12,790 ms |          1,981 | 未通过             |

- Webhook SQL 500/s 漏发 607 次尝试，其中 358 次为首次发送尝试；部分后来通过重复投递到达，最终 353 个唯一首次事件未到达 SDK。这轮不能用于宣称完成了恒定 500/s 负载。
- 内存控制组和 SQL 组使用同一工具、协议、并发及观测配置。WS 500/s、Webhook 400/s 的表现不同，说明新增 SQL 链路影响了本负载的承载表现；Webhook 内存 500/s 也失败，限制不能全部归因于数据库。
- 每个控制点仅一轮；失败组处理量也不同，不将 CPU 差值换算为固定的单条 SQL 成本。
- 共完成 16 个正式样本，测量段计划 1,044,000 个首次事件：12 个样本通过容量标准，15 个通过完整性检查。所有短测和分账号结果见 [JSON](sql-capacity-2026-10-21.json)。

## 工具修正与检查

- 新增真实 SQL 模式、用途受限的显式数据库文件、每轮资料预载、查询统计及 schema 清理，操作见 [分布式基准](benchmark-distributed.md#真实-sql-模式)。
- 首次双 Webhook 冒烟出现 578 次 403：工具把 A 的账号头用于 B 的 URL。框架拒绝正确；现已按账号生成请求头，并增加真实双账号 Webhook 回归。失败及修正后的成功记录分别保留。
- 一次启动因本机工作目录错误，在连接前退出；日志保留，所创建的空目录已删除，不计入容量样本。
