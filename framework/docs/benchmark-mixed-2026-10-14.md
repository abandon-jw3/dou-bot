# 混合负载 Benchmark：2026-10-14

本轮针对 2,000 群场景测量本机 Webhook 的接纳、业务完成、排队、延迟与资源回收。基于 SDK 0.8.0；本轮另外修复了 Webhook 过载时的连接复用，修复尚未发布。公开 API、版本号和依赖不变。

## 测量方式

- 独立 SDK 子进程：实际 HTTP 监听、JSON 解析、Ed25519 验签、路由、Guard、参数绑定、中间件、处理器及回复。
- 独立发送与服务夹具进程：按计划时间持续发送，模拟 HTTP 业务服务与 QQ API。发送端的 CPU、内存及调度延迟另记。
- 固定到达率不等待前一条业务完成。HTTP 503 最多追加两次模拟重试，间隔为 100 / 200 ms；这不是 QQ 平台的重试承诺。
- 完成延迟从计划到达时刻起算，包含发送端迟到和服务端排队。成功与所有终态分别统计；分位数采用 1 ms 桶的上界，超过 60 秒的值不丢弃。
- 吞吐区分首次事件、重试、重复投递、对话回答、HTTP 接纳与业务成功。拒绝处理速度不算业务吞吐。
- 运行中不强制 GC；每秒记录 SDK 资源、RSS、堆、CPU 和事件循环延迟。RSS 包含 Node、HTTP 与测量代码，不代表 SDK 净占用。
- 未连接真实 QQ、数据库、Nginx、TLS 或远程服务器；输入类型和业务耗时是本轮假设。

## 负载与配置

| 配置              | 本轮取值                                                             |
| ----------------- | -------------------------------------------------------------------- |
| 群与场景          | 2,000 个可选群；约 85% 群聊、15% 私聊；约 20% 群流量集中于一个热点群 |
| 执行容量          | 32 并发、2,000 排队项、32 MiB 事件保留字节                           |
| 缓存容量          | 50,000 去重记录、200,000 回复范围；使用默认有效期                    |
| 上下文 / API 超时 | 1,800 / 1,200 ms                                                     |
| prompt            | 最多 512 个；单步等待 1,500 ms                                       |
| 发送端保护        | 256 条 HTTP 连接、最多 2,048 个在途请求；触顶则记录漏发并使本轮失败  |
| 关闭实验          | 保留 8 个等待会话，再投递 40 个慢任务；排空期限特意设为 800 ms       |

以上是压测配置，不修改 SDK 默认值。已接纳的 prompt 恢复执行时会重新入队，因此瞬时排队数可能略高于新任务的队列容量。

- 命令混合：40% 参数与 normalize / 上下文查询、10% 角色权限、10% 附图、10% DOCX、10% 按钮、13% 多轮、4% 图片上传、2% 错误参数、1% 主动业务异常。
- DOCX 同时命中两个处理器，各自加载上下文并回复；校验每个处理器至多执行一次。
- 多轮：60% 两步回答、20% 取消、20% 故意不答；插入错误用户的回答以及重复投递，校验身份与回复目标。
- 普通数据请求约 15 ms，5% 长尾约 450 ms，另有少量更慢请求；QQ API 夹具基础延迟约 15 ms。部分查询执行 3 ms 同步计算。
- 大消息阶段：64 KiB 文字和 120 ms 数据请求。图片路径包含 64 KiB 合成数据的编码与 HTTP 上传，不验证图片内容。
- 故障阶段：按固定事件编号注入 429、503、数据与 API 超时；另外让一次 Token 刷新失败，检查并发刷新与恢复。
- 负载结束后先排空，再单独进行有活动任务、排队任务和 prompt 的关闭实验。

## 压测发现的修复

- 优化前的完整负载在高峰产生大量 `EADDRNOTAVAIL`，发送端开始丢弃请求，不能据此计算框架的高峰吞吐。
- 实测发现：正文已读完、验签已通过的请求，在队列过载返回 503 时仍被强制关闭连接。重试增加新连接数。
- 独立连接测试复现：连续 100 次过载响应使用了 100 条 TCP 连接；优化后复用 1 条连接，释放队列后继续正常接纳。
- 修复仅允许上述过载响应复用连接。非法签名、超大正文、未读完请求占满接入名额及停止接收的响应继续关闭连接。
- 是否复用仍由客户端决定。本轮验证的是本机 HTTP 客户端；尚未重新进行真实 QQ / Nginx 联调。

## 实测结果

**未全通过：2,500 次/秒突发档出现 18 次 TCP 连接重置。** SDK 业务一致性与关闭清理通过，但不能把这一档当作无错误承载能力。

环境为 Apple M4 / 10 核 / 32 GiB、macOS ARM64、Node 24.21.0、TypeScript 5.9.3。最终配置完整运行一次，共 350 秒、149,750 条计划首次事件，覆盖全部 2,000 个群标识。另有 377,661 个 HTTP 响应（含重试和对话），以及上述 18 次连接错误；发送端主动漏发为 0。

| 阶段（首次事件/s） | 已接纳/计划首次事件 | 成功完成/s | 成功 P95 / P99（ms） | 最高采样排队数 |
| ------------------ | ------------------: | ---------: | -------------------: | -------------: |
| 50                 |       3,000 / 3,000 |       46.4 |          478 / 1,540 |              0 |
| 200                |       9,000 / 9,000 |      185.5 |          475 / 1,538 |              0 |
| 500                |     22,500 / 22,500 |      430.2 |        5,291 / 8,301 |          1,573 |
| 1,000              |     21,564 / 45,000 |      434.9 |      10,926 / 11,384 |          2,002 |
| 2,500 突发 †       |      9,180 / 50,000 |      423.8 |      11,155 / 11,528 |          2,002 |
| 大消息 500         |      4,070 / 10,000 |      277.1 |        4,591 / 4,918 |          2,000 |
| 故障 150           |       6,750 / 6,750 |       85.2 |      23,448 / 33,472 |          1,896 |
| 恢复 50            |       3,000 / 3,000 |       68.7 |      13,139 / 15,033 |          1,885 |

- 成功完成/s 和最高排队数按实际时间分段，完成量包含前一阶段积压；接纳计数和成功延迟按**首次事件所属阶段**分组，不能直接互除。恢复阶段完成率高于 50/s，包含正在排空的旧任务。
- 成功指按预期完成业务，包括计划中的取消/超时流程；Guard 拒绝、参数错误、故意业务异常及下游失败另计。多轮的 P99 包含设计为 1,500 ms 的等待。
- 50 / 200 阶段无采样排队。500 阶段虽然最终全部接纳，但队列持续增加，成功 P95 达到 5.29 秒；本轮不能称其可持续稳定承载 500/s。
- † 突发档全部计划事件进入发送流程，其中 18 次请求连接被重置，计入失败，原始报告保留非零退出状态。SDK 未出现非预期处理错误。连接重置的具体原因尚未定位，需要独立压测机或连接级抓包对照。
- 故障后降回 50/s，约 **18.8 秒**观察到队列归零，并在余下恢复阶段维持为零；精度受约 1 秒采样间隔限制。
- 发送调度 P99 各阶段为 6～7 ms，单次最大延迟约 32.8 ms；最多 576 个请求在途，低于本轮 2,048 上限。

## 资源与正确性

- SDK 最高采样 RSS **512.6 MiB**，最高堆 **221.3 MiB**；事件保留字节最高约 **32.0 MiB**。事件预算并不是整个 Node 进程的内存上限。
- 200 / 500 / 2,500 阶段平均 CPU 分别约 0.37 / 0.45 / 0.71 核。最高单采样区间的事件循环 P99 约 18.5 ms；这不是全程所有事件循环样本的统一分位数。
- 单个处理器重复执行、错误身份/群回复、重复回复序号、上下文串用的断言失败均为 0；多轮收到回答 5,682 次、取消 1,892 次、计划超时 1,972 次。
- 执行了 2,967 次合成图片上传、7,594 次按钮确认。Token 请求 60 次，最多 1 个并发刷新；注入过一次刷新失败。
- 下游故障注入覆盖 HTTP 429 / 503、数据超时与 API 超时。它们导致的业务失败被计入结果，没有归为成功吞吐。
- 关闭前存在 32 个活动任务、8 个排队任务和 8 个等待会话；约 **839 ms**返回预期的 SHUTDOWN_TIMEOUT。关闭后队列、保留字节、缓存、任务、信号、定时器及会话均归零，48 个测试执行全部取消。
- 关闭并 GC 后堆约 **15.4 MiB**；测量数组和报告仍在内存中。短时资源归零不能证明多日运行无泄漏。

## 证据与边界

- 汇总、逐阶段指标、源码及测试程序指纹见 [JSON 报告](benchmark-mixed-2026-10-14.json)。原始报告位于 work/mixed-benchmark/standard-20261014-d.json 及其 .sdk.json / .driver.json 文件。
- 原版 SDK 的完整尝试发生 EADDRNOTAVAIL；修复连接复用后的首次完整尝试不再发生端口错误，但压测端 512 个在途上限漏发 108 次，故扩大为 2,048 后得到本报告。另一次早期尝试因报告 IPC 回传不完整作废。所有记录保留，未覆盖或混入最终统计。
- 增加了大报告落盘、分位数、确定性负载、签名及连接复用回归。故意返回错误用户的反例也确实触发身份断言，没有把错误响应当作成功。
- 未控制后台应用、CPU 频率或机器独占。这里没有统计置信区间，也不能把一次本机运行外推为真实 QQ 配额、远程服务器容量或多日稳定性。
- 每群每天 50 次、共 2,000 群仍只是业务量假设；真实峰值、数据库耗时和下游限流需要另测。

## 复测

在 framework 目录运行，每轮使用不同标签：

```sh
npm run benchmark:mixed -- smoke local-smoke
npm run benchmark:mixed -- standard local-standard
```

- smoke 约 11 秒，使用较小容量验证过载、故障与资源清理。
- standard 约 6 分钟：预热 → 50 / 200 / 500 / 1,000 次每秒 → 2,500 次每秒突发 → 大消息 → 故障 → 恢复。
- 每轮在 work/mixed-benchmark 保存总报告与两个子进程原始报告；报告重名会在开始前拒绝。
- SDK 源码、测量程序指纹、Node、硬件、配置及失败原因均写入报告。中断和失败记录保留，不混入成功结果。
- 反例校验：设置 `DOU_BOT_BENCHMARK_CORRUPT_DATA=1` 运行 smoke，模拟服务会返回错误用户，命令应失败且记录身份断言错误。

旧的串行测试继续作为微基准保留，见 [执行器微基准](benchmark-2026-10-14.md)。它与本轮的业务负载、入口和计时方式不同，不能直接比较吞吐数字。
