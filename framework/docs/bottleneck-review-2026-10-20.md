# 高负载阶段定位与优化（2026-10-20）

**完成阶段观测和两项代码优化；当前配额下仍不能认定稳定 500 次/秒。** 基线 400/s 的关闭/开启指标各两轮通过。候选 B 在 128/32 下通过一轮、失败一轮；改为 128/64 后两轮均失败，不提高框架默认并发。

## 范围与计数

- 单账号、2,000 个合成群标识；发压端在本机，服务器运行 SDK、模拟 API 与监督进程，共享 1.5 核 / 1 GiB，禁用测试组 swap；SSH 在组外。
- 每轮 10 秒 200/s 预热、5 分钟指定速率、15 秒 200/s 恢复，再排空；每轮独立实例。保持原缓存容量、TTL、验签、128 条输入连接和 2,048 个在途请求上限。
- 不包含真实 QQ、SQL、Nginx/TLS 或图片渲染；不能推断 WS 容量，也不是多日生产稳定性证明。
- 表中计数是首次事件，包含预设的权限拒绝、参数错误和业务异常；不等于消息发送数。部分完成发生在恢复期，不能直接用完成数除以 300 秒声称稳态吞吐。
- 成功 P95 为发压端单调时钟下的直方图上界，包含 SSH 输入及完成通知返回；尾队列取最后最多 30 个采样点的中位数。完整性与容量分别判定。

## 测量工具修正

- 每约 5 秒保存累计指标、采集耗时和在途状态；由相邻计数/分桶差分计算窗口分位数。跨阶段窗口单列，不能相减累计 P95 或最大值。用法见 [分布式基准](benchmark-distributed.md)。
- 首次指标轮的 28 MB 报告未完整取回，随后监督进程收尾失败；远端原文已恢复并核对 SHA。改为发压结束后用独立压缩连接传输、成功后原子改名；同一报告实测约 3.6 秒取回。输入连接未压缩。
- 另一次预试发生 5 次复用连接重置。发压端现于空闲 2 秒后回收连接，活动请求仍保留 10 秒超时；两版 Node 和 Linux 的实际 HTTP 回归通过。连接错误仍记录为失败，不自动重试。
- 上述失败与修正前源码分别保留。下表使用同一正式工具指纹；未删除失败样本来制造通过。

## 定位与代码修改

- 基线首轮 500/s 指标窗口：入站排队平均约 4,124 ms，出站排队约 126 ms，QQ HTTP 约 70 ms；参数绑定约 0.013 ms。prompt 挂起与夹具中预设的慢接口不属于框架 CPU 热点。
- 单独在负载起点后约 179–199 秒采集 CPU profile。该轮有额外采样开销，不计入容量表；采样窗口内队列增长，不能单独归因于 profiler。主线程墙钟加权样本中，GC 约 13.56%，FrameworkError 构造约 4.15%，接纳函数自身约 3.01%；位置采样集中在反复读取 Map 首项的代码。嵌套比例不可相加，也不等于所有线程的真实 CPU 分配。
- 正常处理结束时，只有存在待取消的 prompt 才创建取消错误。保留取消原因、错误类型和执行顺序，减少无用错误栈分配。
- 缓存达到容量时复用顺序游标，避免每次重新从 Map 开头扫描。过期清理、索引为空和关闭时释放游标；保持淘汰次序、活动项保护、TTL 和回复序号。
